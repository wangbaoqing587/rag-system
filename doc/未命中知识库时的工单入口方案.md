# 未命中知识库时的工单入口：方案 A vs 方案 C

帮助中心 SSE 问答在向量检索为空时，需要展示可点击的工单卡片，而不是只生成一段兜底文案。两种方案都不做第二次知识库检索，判定依据都是当次 RAG 的检索结果。

- 方案 A：已落地
- 方案 C：未实现，作对照

## 结论

继续用方案 A。空检索是后端事实，应用结构化 SSE 事件 `ticket_offer` 表达，不要让模型用自然语言或固定标记转述这个事实。方案 C 只在不能改 Advisor / SSE 协议时作为退路。

| 指标 | 方案 A | 方案 C |
| --- | --- | --- |
| 检索次数 | 1 次 | 1 次 |
| 空检索时模型调用 | 0 | 1 次 |

## 问题与约束

现有 `VectorStoreDocumentRetriever` 在 `similarityThreshold=0.5`、`topK=3`、`docType=help_center` 下可能返回空列表。原先 `ContextualQueryAugmenter.allowEmptyContext(false)` 会把空上下文写成 prompt，模型再生成兜底话，前端只能当普通气泡渲染。

前端 `help-center-app` 已具备 `ticket_entry` 卡片和 `EventSource` 的 `ticket_offer` 监听，缺口在后端如何把「检索为空」变成这个事件，而不是再搜一遍知识库。

对照范围：rag-system 帮助中心 SSE 问答。不含工单创建接口本身。方案 B（前端识别兜底文案）已排除，不列入本文。

## 方案 A：检索为空时发 SSE 事件

判定发生在 RAG Advisor 内部的当次 `retrieve()`。空则短路，不调用 ChatModel；由 `HelpController` 发送命名 SSE 事件，前端走已有 `onTicketOffer`。

### 调用链

1. `HelpCenterApp.doChatByStream` 查询重写后走 `ChatClient.stream()`，挂 `HelpCenterRagAdvisor`
2. `HelpCenterRagAdvisor.prepare()` 调用同一个 `DocumentRetriever.retrieve(query)`
3. `documents.isEmpty()` → context 写入 `ticket_offer=true`，不调用 `chain.nextStream()`
4. 有文档 → `QueryAugmenter.augment` 后 `nextStream`，正常流式生成
5. `HelpController.chatSse` 若 `event.ticketOffer()`，发送 `event: ticket_offer`，payload 为 `suggestedDescription`
6. 前端 `streamChat` 的 `addEventListener('ticket_offer')` 插入 `TicketEntryMessage`

### 关键实现点

| 位置 | 职责 |
| --- | --- |
| `HelpCenterRagAdvisor` | 唯一检索点；空则短路模型，把标记放入 `ChatClientResponse.context` |
| `HelpCenterApp.StreamEvent` | 把 context 标记映射成 `ticketOffer` / `chunk`，`suggestedDescription` 用用户原问题 |
| `HelpController.chatSse` | `SseEmitter.event().name("ticket_offer").data(json)` |
| `helpCenter.js` | 已有监听，无需为方案 A 新增协议 |

相关源码：

- `src/main/java/com/wbq/ragsystem/rag/HelpCenterRagAdvisor.java`
- `src/main/java/com/wbq/ragsystem/app/HelpCenterApp.java`
- `src/main/java/com/wbq/ragsystem/controller/HelpController.java`
- `help-center-app/src/api/helpCenter.js`

## 方案 C：空检索 prompt 输出固定标记

检索仍留在 `RetrievalAugmentationAdvisor` 内。空列表时 `ContextualQueryAugmenter` 把用户问题替换成「必须原样输出标记」的 prompt，模型继续生成；前端在流式文本里识别标记，再替换成工单卡片。

### 调用链

1. 保持 `RetrievalAugmentationAdvisor` + `HelpCenterQueryAugmenter`
2. 把 `emptyContextPromptTemplate` 改成强制输出固定串，例如 `[TICKET_OFFER]`
3. 空检索仍调用模型，SSE 仍走默认 message 事件
4. 前端累积 chunk，全等或包含标记时删掉助手气泡，push `ticket_entry`
5. 命中路径不变：有文档则正常流式回答

### 关键实现点

| 位置 | 职责 |
| --- | --- |
| `HelpCenterQueryAugmenter` | 空上下文 prompt 要求原样输出标记，禁止解释、禁止改写 |
| `RetrievalAugmentationAdvisor` | 沿用框架检索；空时不短路，继续 `nextStream` |
| `HelpController` | 可保持只转发 content，不增加命名事件 |
| 前端 stream 累积 | 流结束或出现标记后替换 UI；需处理半截标记、模型加前后缀 |

## 优缺点对比

| 维度 | 方案 A 结构化事件 | 方案 C 固定标记 |
| --- | --- | --- |
| 空检索判定 | `retrieve()` 返回空列表，确定性事实 | 模型是否听话输出标记，非确定性 |
| 二次检索 | 无，Advisor 内当次 retrieve | 无，Advisor 内当次 retrieve |
| 空检索是否调模型 | 否，短路 `chain.nextStream` | 是，多一次生成延迟和费用 |
| 流式体验 | 直接出工单卡片，无闪烁气泡 | 可能先打出标记再替换，或中途露出 `[TICKET_OFFER]` |
| 协议 | SSE 命名事件，前后端契约清晰 | 把控制信号藏在自然语言信道里 |
| 改动量 | 已实现：自定义 Advisor + Controller 分流 | 后端改 prompt，前端加解析；Advisor 可不动 |
| 模型升级风险 | 与模型无关 | 换模型、改温度、加记忆后标记可能被改写 |
| 误判 | 只取决于阈值和 filter，可调检索参数 | 漏判（没输出标记）或误判（正文碰巧含标记） |
| 同步接口 `/chat/sync` | 同一 Advisor 可短路，但无 SSE 卡片 | 返回值带标记，调用方同样要解析 |
| 可观测性 | 日志 empty retrieval / ticket_offer 即可 | 需对比「检索空」与「模型是否输出标记」是否一致 |

## 选择考量

优先选 A：

- 工单入口是产品控制流，不是模型要「说」的内容
- 前端已经按 `ticket_offer` 设计，A 是补齐契约，不是新协议
- 空检索省一次 LLM，首包更快，费用更低
- 判定与相似度阈值、filter 对齐，调检索即可调行为

才考虑 C：

- 不能改 Java Advisor，只能改 prompt 和前端
- SSE 被网关限制，只能发默认 message 事件
- 需要模型顺带生成一句安抚文案，并接受标记不稳定
- 即便走 C，也必须把标记做成机器协议，而不是关键词模糊匹配（那是已否决的方案 B）

## 落地建议

当前仓库已按 A 实现。验证重点：问知识库没有的问题应只出工单卡片；问充值/退款等文档内问题仍流式回答。

若 A 在运行时出现「有检索结果却出工单」或「无结果仍生成」，先查 `HelpCenterRagAdvisor.prepare()` 的空列表判断和 `similarityThreshold`，不要切 C。

方案 C 的唯一合理形态是「强制原样输出不可自然语言化的标记 + 前端全等匹配」。只要模型仍可能改写，C 就会退化为方案 B，不可用。
